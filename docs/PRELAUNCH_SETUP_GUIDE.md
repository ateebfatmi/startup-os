# CrewVilla prelaunch setup guide

## Identify targets and obtain approval

Record the Vercel team, project ID, Preview branch, canonical HTTPS origin and exact release revision. Record the dedicated Supabase organization, project ref, API host and direct database host. Check both projects' owners, data inventories, aliases, and environment scopes. Use exactly one CrewVilla Supabase project and one CrewVilla Vercel project. The protected Preview is a deployment within the launch project and uses the same Supabase project that will serve the public release. Creation, configuration, deployment, migrations, hosted fixture writes and provider setup each require explicit approval for the exact target and operation.

## Prepare the environment

1. In the approved dedicated Supabase project, use synthetic accounts and fixtures. Confirm backups and a supported restore path. Configure the Auth site URL and allowlist `https://<protected-preview-host>/auth/callback` and the same origin's `/auth/callback?next=**` pattern for variable invitation return paths. Verify the full confirmation, invitation, and recovery URLs after configuration. Password recovery returns through the callback to `/reset-password`. Enable Email and Confirm email, and configure approved custom SMTP for disposable inboxes outside the Supabase team. Vercel protection does not gate direct Supabase Auth requests. Keep signup closed outside approved signup tests. Google Auth uses the callback shown by Supabase and a separate OAuth client.
2. In the approved dedicated Vercel project, select Node 24 and a prelaunch Preview branch. Inspect Git-triggered deployments before linking or pushing. Enable Vercel Authentication under Settings → Deployment Protection. Use a protected Preview URL, grant access to named testers, and verify an incognito browser cannot load the site or its API. Create the Vercel project without triggering an initial Git import deployment. Configure protection before linking Git or initiating a build. Keep automatic Production deployment disabled during testing and leave production domains unassigned to a release. Set the public and server-only values from the [environment audit](PHASE2_ENVIRONMENT_AUDIT.md) in the relevant Preview scope. Leave providers disabled initially. Never copy production scopes, aliases or credentials.
3. Keep the canonical origin identical in `NEXT_PUBLIC_SITE_URL` and `CREWVILLA_PRELAUNCH_ORIGIN`. Use the prelaunch Supabase ref and set `CREWVILLA_PRELAUNCH=1`. Run `node scripts/prelaunch-preflight.mjs` using the reviewed environment before a build or any hosted test. Keep actual environment files out of source control.
4. Inspect the pending migration list against prelaunch's history. Review schema changes, locks, data preservation, private Storage bucket settings and Realtime policies. Load the direct prelaunch database connection into the local process as `CREWVILLA_PRELAUNCH_DATABASE_URL` and run `node scripts/prelaunch-preflight.mjs --migration`. Pooler URLs are intentionally rejected. This command makes no connection and applies no SQL. An authorized operator must verify dashboard identity and backup evidence, then apply only the approved pending migrations using the same verified target and credential. Stop if the applied history or host differs.
5. After explicit deployment approval, build the exact reviewed revision using `npm ci` and `npm run check`, then deploy to the approved Preview scope. Do not use production promotion or a production alias. Run `node scripts/prelaunch-preflight.mjs --smoke` against the approved origin. This read-only probe fails on redirects, an unconfigured backend or a project-ref mismatch. It requires an approved local `VERCEL_AUTOMATION_BYPASS_SECRET`, checks that unauthenticated access is blocked, and checks project identity with the bypass header. Keep the secret out of URLs, source control, browser-wide headers, and test evidence.
6. Disable public Realtime access on the dedicated Supabase project after approval. Verify that authenticated members can join private topics and that outsiders cannot. Confirm the Storage bucket remains private, and test its policies with normal user sessions.
7. Configure TURN through a dedicated credential issuer with short lifetimes, server-only token, and agreed quota. Exercise relay selection before calling it verified. Enable each optional provider separately after approval. Stripe uses test mode, prices and `/api/billing/webhook` from the same test account. Register exact `/api/integrations/{provider}/callback` URLs for each workspace OAuth provider. Test separate accounts and synthetic data only.

## Backup, recovery and public release

Before any migration, capture the applied migration history, check the project's backup retention and latest recoverable point, and record the recovery owner. If managed backup coverage is insufficient, prepare an encrypted off-project logical export and verify it in disposable local PostgreSQL. Export Storage object bytes separately from database metadata and keep a protected manifest. Record Auth, Realtime, provider, and Vercel configuration without secret values.

For a bad deployment, keep protection enabled and roll back the app to a schema-compatible deployment on the same Vercel project after approval. For database issues, stop writes, preserve evidence, and prefer a reviewed forward fix. In-place restore, fixture deletion and account cleanup require separate approval. Confirm the scope of data loss and the Storage reconciliation plan before restoring. Recheck Auth, Storage, RLS, Realtime, and health after recovery.

Public release requires separate approval. Keep the same two projects. Inventory and explicitly approve any cleanup of synthetic accounts and data, revoke test sessions and automation bypass, configure the canonical public origin and the equivalent Supabase Auth callback rules scoped to it, and build a Production deployment with the same Supabase ref and public origin. Leave `CREWVILLA_PRELAUNCH*` out of the Production scope. Review the protected candidate and release plan before assigning or opening the public domain. Keep Stripe test-only and unverified optional providers disabled until their separate approvals.

- Release evidence should include the Vercel deployment ID, Git revision, Supabase ref, migration history, and health result without secrets. Use the test matrix and multi-user procedure for approval-dependent test writes.
- For app rollback, stop testing and return the dedicated prelaunch alias to a compatible, known-good prelaunch deployment after approval. Recheck health and run smoke tests. Forward-only database fixes preserve data. Rehearse recovery locally without provisioning additional hosted resources.
- Revoke prelaunch test sessions and provider connections when finished. Rotate credentials in the originating provider and update only the prelaunch scope. Rebuild after changing public build-time settings. Preserve encrypted integration data when rotating its encryption key, or explicitly revoke and reconnect synthetic accounts.
- For teardown, verify identities again, archive scrubbed evidence, disable callbacks and webhook delivery, remove the prelaunch alias, and request explicit authorization before deleting synthetic fixtures. Retain the two launch projects. Never reset a shared project.

## Guarded independent-session browser test

After approving synthetic account sign-in and creating the fixture through the acceptance procedure, load these values into the local process from a private secret store:

- `VERCEL_AUTOMATION_BYPASS_SECRET`

- `CREWVILLA_PRELAUNCH_FIXTURE_WORKSPACE_ID` and `CREWVILLA_PRELAUNCH_FIXTURE_PROJECT_ID`
- `CREWVILLA_PRELAUNCH_OWNER_EMAIL` and `CREWVILLA_PRELAUNCH_OWNER_PASSWORD`
- `CREWVILLA_PRELAUNCH_MEMBER_EMAIL` and `CREWVILLA_PRELAUNCH_MEMBER_PASSWORD`
- `CREWVILLA_PRELAUNCH_OUTSIDER_EMAIL` and `CREWVILLA_PRELAUNCH_OUTSIDER_PASSWORD`

The project belongs to the fixture workspace. Owner and member must be verified users with access. The outsider is a verified user without access. All accounts are synthetic. Set `CREWVILLA_PRELAUNCH_APPROVED_SIGNIN=1` only after explicit approval for this target and these accounts.

Run `node scripts/prelaunch-preflight.mjs --smoke` followed by `npx playwright test --config playwright.prelaunch.config.mjs`. The suite also checks health itself before sign-in, uses fresh browser contexts, and disables traces, videos and screenshots. Sign-in creates Auth sessions. The project check makes read requests. This test covers a narrow project read boundary, and the test matrix tracks the remaining writes, independent persistence, Storage, Realtime, and physical media steps.
